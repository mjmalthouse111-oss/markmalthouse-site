Accessibility Conformance Report, International Edition (based on VPAT® Version 2.5Rev INT)

Moodle LMS 5.3 (default install): Sample Accessibility Conformance Report

SAMPLE REPORT. Independent sample evaluation by Mark Malthouse, independent accessibility evaluator. Not produced for, reviewed by, or affiliated with Moodle.

This is a sample, made to show the format and method. It records what was observed on 15 October 2026 on a default Moodle LMS 5.3 install with sample course content, run locally by the evaluator.

Mark Malthouse is not IAAP-certified; each criterion lists exactly how it was tested.

This is a technical assessment, not legal advice and not a determination of legal conformance.

Name of Product/VersionMoodle LMS 5.3 (release package moodle-5.3.zip, downloaded 14 October 2026), default settings, Boost theme, PHP 8.4.26, PostgreSQL 17.11, with a scripted sample course.
Report Date15 October 2026 (testing done on 15 October 2026)
Product DescriptionMoodle LMS is an open-source learning management system used by schools, colleges and universities. This sample covers the learner side of the product as a student and a logged-out visitor see it.
Contact Information

Vendor accessibility contact: not applicable to this sample (in a client report, the vendor's own accessibility contact).

Evaluation party: Mark Malthouse, independent accessibility evaluator, mark@markmalthouse.com.

Notes

Scope. 7 user flows, 13 page states, listed in the "Flows tested" section. Pages outside these flows, teacher and administrator screens, the mobile app, and Level AAA criteria were not evaluated.

Test environment. Moodle LMS 5.3 installed from the official release package with default settings, the Boost theme, PHP 8.4.26 and PostgreSQL 17.11, served on the evaluator's computer. A script created one sample course whose content mirrors Moodle's public demo course: an audio message from the tutor, an online-text assignment, a quiz with multiple-choice and matching questions, a forum and a graded item. A test student account was used for all flows except login.

Platform and content. Remarks say "Platform" for issues in Moodle LMS itself and "Sample content" for issues in the course material, which a real customer would write themselves.

User tours. Moodle's first-visit user tours were marked as completed for the test student so they did not cover the pages under test. The tours themselves were not evaluated.

Evaluation Methods Used

Automated checks: axe-core 4.13.0 (through @axe-core/playwright) run on every page state, all rule sets, results saved as JSON. Playwright 1.64.1 driving Chromium 156.0.8078.4 on Windows 11; Firefox 157.0 used to repeat the quiz keyboard test.

WCAG 2.2 and timing checks: focus-not-obscured sampling at each Tab stop (2.4.11), target size measurement with the spacing exception (2.5.8), paste and autocomplete checks on login (3.3.8), and the session timeout warning tested with the timeout shortened to 5 minutes through Moodle's admin/cli/cfg.php (2.2.1). Windows contrast themes were emulated with forced colours.

Keyboard-only walkthrough: every flow was completed with the keyboard (Tab, Shift+Tab, Enter, Space, arrow keys, Escape, Alt+F10). On each page state the Tab key was pressed through the whole page (251 unique Tab stops; repeats caused by the quiz defect are not counted), logging each focused element and comparing focused and unfocused screenshots pixel by pixel to check for a visible focus indicator.

Zoom and reflow: each page state rendered 320 CSS px wide (400% zoom of a 1280 px wide window) and 640 CSS px wide (200%), and in portrait at 768 x 1024, checking for sideways scrolling and cut-off content, with screenshots.

Colour contrast: axe-core text contrast checks; border contrast of form controls computed from styles; pixel sampling of screenshots where text sits over images.

Screen-reader-relevant markup inspection: the Chromium accessibility tree (what screen readers read) saved for each page state, plus scripted checks of accessible names, roles, states, landmarks, headings, form labels and error links, live regions, label-in-name, and language attributes. Text spacing was tested by injecting the WCAG 1.4.12 values.

Screen reader: NVDA 2026.2 with Chrome 156.0.8078.4 and Firefox 157.0, driven by Guidepup automation; spoken output logged and reviewed (login, quiz in focus and browse modes, forum form, forum Message editor and errors, session timeout warning). No testing by people with disabilities.

Limits. Markup inspection shows what a screen reader is given, not how it announces it. Automated tools find only part of accessibility problems, which is why each criterion also lists the manual checks used.

Terms

The terms used in the Conformance Level information are defined as follows:

  • Supports: The functionality of the product has at least one method that meets the criterion without known defects or meets with equivalent facilitation.
  • Partially Supports: Some functionality of the product does not meet the criterion.
  • Does Not Support: The majority of product functionality does not meet the criterion.
  • Not Applicable: The criterion is not relevant to the product.
  • Not Evaluated: The product has not been evaluated against the criterion. This can only be used in WCAG Level AAA criteria.

2.1.1 KeyboardPartially Supports

Platform (quiz attempt): when a multiple-choice question has no answer selected, pressing Tab on its first option does not move focus. After 26 more Tab presses focus was still on option a, in both Chromium 156 and Firefox 157. A keyboard user cannot Tab past an unanswered question; the only ways on are to pick an answer with the arrow keys (which records an answer the student may not want) or to use the quiz navigation drawer. The hidden "Clear my choice" radio is checked, focusable and inside aria-hidden.

With NVDA 2026.2: in focus mode (Tab), five more Tab presses on option a produced no speech in Chrome or Firefox, because focus did not move. In browse mode NVDA is not blocked: with Firefox, H moved from "Question 1, heading, level 3" to "Question 2, heading, level 3" and the arrow keys read question 1's status, its question text and its first option; F (next form field) moved on to the question 2 drop-downs in Firefox and through later questions in Chrome. So sighted keyboard users, switch users and screen reader users who use Tab are blocked; screen reader users moving in browse mode can get past.

Known to Moodle: MDL-89285 "qtype_multichoice: Keyboard trap prevents Tab navigation past unanswered single-answer questions" (affects 5.3; status "Component lead review in progress" on 15 October 2026). The older MDL-67188 was closed as a duplicate of MDL-69116, fixed in Moodle 3.8.5 and 3.9.2 in September 2020; the current defect is a later problem.

Everything else in the flows worked by keyboard alone: login, dashboard filters, course index, audio player, the text editor (including Alt+F10 for its toolbar), saving a submission, posting to the forum, the quiz submit dialog and the session timeout dialog.

How tested: keyboard-only walkthrough; repeat test with Tab key presses only, from the top of the page, in Chromium 156 and Firefox 157.

Advisory notes

These do not change any conformance level above but are worth fixing.

  • After a failed login the page reloads with the error in a role="alert" box and focus in the username field, but NVDA read only the page title ("Log in to the site Sample U") in Chrome and Firefox; the error was not announced. Linking the error to the field (aria-describedby and aria-invalid) would make it heard. This may be a test timing effect; a manual NVDA check is recommended.
  • When the session timeout warning appeared, NVDA spoke nothing in the following 3 seconds (see WCAG 2.2.1). A manual check with a screen reader user is recommended.
  • Heading levels skip in places (for example h1 to h3 on quiz and assignment pages). Not a WCAG failure, but it makes heading navigation less predictable.
  • The activity description and dates on assignment and quiz pages sit outside the main landmark, so landmark navigation lands below the instructions.
  • After Alt+F10 moves focus to the editor toolbar, Escape leaves focus on the toolbar instead of returning it to the text.
  • During the first second after the editor loads, axe reported an unnamed word-count button and a resize handle without aria-valuenow; both were correct once loading finished.
  • In Windows contrast themes (forced colours), the quiz flag icon disappears; its text label stays, so no information is lost.
